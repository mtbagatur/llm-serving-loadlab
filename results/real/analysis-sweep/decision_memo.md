# Decision memo: where is the latency?

_Data: real run, Ollama 0.6.8 + qwen2.5:0.5b on CPU (8 pinned cores), short sweep with ITL (see README). Generated by `loadlab.analyze`; every number below comes from the CSVs listed in summary.json._

**Scenario analysed:** `sweep-itl`  |  **requests:** 48  |  **errors:** 0

## Finding

**Verdict: `prefill`.** Latency tracks prompt length, and for the longest prompts most of it is time-to-first-token: the bottleneck is prefill on the serving device.

| driver | elasticity of latency | variance explained alone (R^2, log scale) |
|---|---|---|
| prompt length | 1.07 (2x prompt -> x2.10) | 0.76 |
| concurrency | 0.96 (2x in-flight -> x1.95) | 0.22 |

TTFT elasticities: prompt 1.47, concurrency 0.92. At the longest prompt, TTFT is 93% of total latency (median over concurrency levels).

Throughput changes by x0.96 when in-flight requests go from 1 to 4 (x4 more load, median over prompt lengths). The serving device is already saturated: extra requests wait in line, they do not get processed faster.

With a single request in flight, going from ~146 to ~1882 prompt tokens moves median latency from 1.50s to 19.24s: that cost exists with no load at all.

## Which component is the bottleneck?

Rule: scale one component (gateway/auth replicas, proxy, ...) and rerun the same matrix. If tail latency changes but per-request decode tok/s and TTFT-vs-prompt-length stay the same, that component was not the bottleneck: it only moved queueing around. If decode tok/s or TTFT at a given prompt length change, it was on the critical path.

## Recommended action

1. Do not scale stateless front services (gateway, auth); they are not where the time goes.
2. Add serving capacity where prefill runs: a second model replica on an idle accelerator, behind the same Service.
3. Reduce prefill work: trim/cap prompt and RAG context length, enable prefix caching for shared system prompts.
4. If the engine supports it, enable chunked prefill so long prompts do not stall decode of other requests.
5. Alert on TTFT p95 split by prompt-length bucket, not only on request rate.

## Caveats

- Elasticities come from a log-log OLS fit on a balanced factorial design; they summarise, they do not prove causality.
- Closed-loop load: concurrency = requests in flight, not requests per second.
- Results are specific to the hardware, engine and model in the run metadata (results/*.json).
